| רכיב | איפה הוא רץ? | מה הוא עושה, במשפט אחד | אנלוגיה לקונדיטוריה |
|---|---|---|---|
| API server | בהנהלה (control plane) | מקבל בקשות כמו `kubectl apply` ודרכו קוראים ומעדכנים את מצב האשכול. | דלפק שמקבל בקשות ומוסר מידע. |
| etcd | בהנהלה (control plane) | שומר את ההגדרות ואת המידע על מצב משאבי האשכול. | פנקס ההזמנות של ההנהלה. |
| scheduler | בהנהלה (control plane) | בוחר באיזה node ירוץ כל Pod שעדיין לא שובץ. | אחראי שיבוץ שבוחר מטבח שיש בו מקום לעמדת עבודה נוספת. |
| controller manager | בהנהלה (control plane) | מפעיל בקרים שדואגים שמצב האשכול יתאים למה שהוגדר, למשל שיהיו שני Pods של `greeter`. | מנהלת שמבחינה שאחת משתי העמדות חסרה ודואגת לפתוח עמדה במקומה. |
| kubelet | בכל node | מוודא שהקונטיינרים של ה־Pods ששובצו לצומת שלו מופעלים, ומדווח על מצבם. | מנהלת משמרת שמוודאת שהעמדות במטבח שלה עובדות. |
| container runtime | בכל node | מפעיל ועוצר את הקונטיינרים בפועל לפי הוראות ה־kubelet. | עובד שמדליק ומכבה את הציוד בעמדות. |
| kube-proxy | בדרך כלל בכל node | מגדיר כללי רשת שמעבירים בקשות מ־Service אל ה־Pods שמאחוריו. | מרכזייה שמעבירה שיחה לאחת מעמדות העבודה הזמינות. |
| CoreDNS | כ־Pods על הצמתים שאליהם שובצו | מתרגם שמות של Services, כמו `greeter`, לכתובות IP שאפשר לפנות אליהן. | ספר טלפונים שמוצא מספר לפי שם. |







כשמריצים `kubectl scale deployment web --replicas=4`, ה־API server מקבל את הבקשה ושומר ב־`etcd` שמספר ה־Pods הרצוי הוא 4. הבקרים ב־`controller manager` מזהים שיש רק שני Pods ויוצרים עוד שניים לפי התבנית של `web`. ה־`scheduler` בוחר צומת לכל Pod חדש, וה־`kubelet` בכל צומת שנבחר מבקש מה־`container runtime` להפעיל את הקונטיינרים. בסוף שני ה־Pods המקוריים ושני החדשים מופיעים במצב `Running`.


אם הקונטיינר של `backend` קורס, ה־`kubelet` מפעיל אותו מחדש **באותו Pod**. אם מוחקים את ה־Pod כולו, ה־`ReplicaSet` מזהה שחסר עותק ויוצר **Pod חדש**. ה־`scheduler` משבץ אותו לצומת, וה־`kubelet` מפעיל בו את הקונטיינר.

כש־`node 2` נכבה, ה־Pods שעליו מפסיקים לעבוד. אחרי זיהוי הכשל, ה־`ReplicaSet` יוצר תחליפים ל־Pods שהוא מנהל, וה־`scheduler` משבץ אותם בצמתים שנותרו אם יש מקום. ב־Docker Desktop יש צומת אחד, אז כשהמחשב נכבה כל האשכול מפסיק לעבוד עד להפעלה מחדש.


מה שיהיה חסר הוא ה־image עצמו על הצומת בענן. קובץ ה־YAML מכיל רק את השם של ה־image, למשל greeter:v1. כשמעבירים את ה־YAML לענן, החבילה שבנית במחשב שלך לא עוברת איתו.

ה־Pod שנוצר עם `kubectl run` היה עצמאי, ולכן כשמחקנו אותו לא היה בקר שייצור אותו מחדש. ה־Pod של `web` נוהל על ידי `ReplicaSet` של ה־Deployment, שזיהה שחסר עותק ויצר Pod חדש. כדי שגם `stats` ייווצר מחדש אחרי מחיקה, נגדיר לו Deployment עם `replicas: 1`.
